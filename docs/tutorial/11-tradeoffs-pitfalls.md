# 11 設計取捨與踩坑紀錄

本章素材來自 `docs/01-system-analysis.md` 的 🔶 決策點（2026-11-09 使用者確認）、README「設計取捨與已知限制」、fix 類 commit 訊息，以及 2026-11-11 的開發對話。

## 第一部分：設計取捨

### 取捨 1：行車時間用「L1 取樣路徑快取 ＋ L2 精確驗證」

- **決策**：最佳化用 L1（取樣時刻的最佳路徑，以實際出發時刻精確積分），最終裁決用 L2（點對點 TD A\*）。
- **考慮過的選項**：只用精確 A\*（不快取）；精確 profile search（分段線性到達函數）；取樣時刻之間線性內插。
- **選擇與理由**：📄 `docs/01-system-analysis.md` §4.6：前者每秒只能做數千次查詢，品質差；profile search 在 2 萬節點 × 200 站下預處理時間與記憶體不可控；L1 能同時保證「上界、取樣點精確、FIFO」。使用者於 2026-11-09 確認（🔶 決策 1）。
- **代價**：📄 README：「L1 在路徑於取樣區間內改變時可能高估幾秒，所以最終一律以 L2 裁決。代價是最佳化中途的比較依據是 L1，極少數情況下 L1 與 L2 的排序會不同。」另外 L2 精確化後可能需要移除或補插站點，增加 `FinalizeExact()` 的複雜度。

### 取捨 2：鎖定站採「絕對位置」

- **決策**：鎖定站固定在原車的第 N 站；為了保證位置不變，該車從第 1 站到最後一個鎖定站全部凍結。
- **考慮過的選項**：A 絕對位置；B 相對順序（鎖定站之間可以插入其他站）。
- **選擇與理由**：📄 `docs/01-system-analysis.md` §4.10：驗收條件寫「仍在原車**原位置**」，A 符合字面。使用者確認（🔶 決策 2）。
- **代價**：📄 README：「比起只鎖相對順序，彈性較小。」鎖定第 10 站等於凍結前 10 站。實作上只需要一個「凍結前綴長度」（`LockSet.FrozenPrefixLength()`），讓 ALNS 與編輯器都很簡單，這是選 A 的隱性好處。

### 取捨 3：出發時刻是決策變數（2026-11-11 修訂）

- **決策**：以前向時間餘裕延後出發，吸收第一站之前與路線中段的等待；工時上限的可行性判定用這個出發時刻。
- **考慮過的選項**：一律最早出發；只消除第一站等待（原 🔶 決策 3）；前向時間餘裕。
- **選擇與理由**：原設計選「只消除第一站等待」。📄 外部審查指出中段長等待（午餐與晚餐之間）也會吃掉工時，而工時上限是硬性條件，所以這不只是政策，會讓可行路線被判成不可行（commit `1a25bf2`）。
- **代價**：每次迭代多幾次排程模擬，大型範例 4 × 6,000 次迭代從 182 秒變 241 秒（📄 README）；相同迭代數下解比較好，60 秒時間上限下兩版結果在隨機差異內。時間相依時是定點迭代的近似。

### 取捨 4：休息只在「需要時」列舉

- **決策**：只在「不休息就會超過 4.5 小時」的位置分支，列舉之前每個可休息的站。
- **選擇與理由**：📄 README：「符合不需要時不插入，也與窮舉一致。」
- **代價**：📄 README：「不會為了避開尖峰而主動多休息一次。」

### 取捨 5：模擬退火用有限懲罰，最佳解用精確字典序

- **決策**：接受準則比較純量（未服務與車輛數乘上以平均每站行車為基準的懲罰），最佳解的更新一律用精確字典序。
- **選擇與理由**：📄 README：「讓搜尋能暫時少送一站或多用一台車，以通過緊時間窗、緊容量下的障礙。」
- **代價**：📄 README：「調參仰賴懲罰基準（平均每站行車時間）。」

### 取捨 6：決定性優先於「用滿所有核心」

- **決策**：固定數量的獨立 run（預設 4），與 CPU 核心數無關；自製亂數。
- **選擇與理由**：📄 `docs/01-system-analysis.md` §5：「同種子同迭代上限 → 完全相同」。
- **代價**：24 核心的機器只用到 4 個 run 的平行度（L1 建置則用滿）；時間上限結束的結果仍隨機器而異。🔍 若想用滿核心，可以增加 run 數，但結果會隨 run 數改變。

### 取捨 7：重新排程時延誤車的站不轉給其他車

- **決策**：已出發的車只能服務自己車上剩下的站；故障車已出發則剩下的站無法服務，未出發則釋出。
- **選擇與理由**：📄 `docs/01-system-analysis.md` §4.12：餐盒在車上，不處理轉運（規格範圍外）。使用者確認（🔶 決策 4）。
- **代價**：延誤嚴重時，某些站即使其他車有空也送不到，會列為未服務並附原因。

## 第二部分：踩坑紀錄

### 坑 1：參考解與正式實作「一起錯」，200/200 也看不出 bug

- **症狀**：外部審查回報實例 34：工時上限 200 秒，路線 [0, 5, 6] 以最早出發計算工時 299（不可行），但延後出發後工時只有 145。我們的 200 組窮舉對照卻是 200/200 全部一致。
- **原因**：評估器只考慮兩個出發時刻（最早出發、第一站不等待）。**參考窮舉器也採用相同的出發政策**，所以兩邊對「可行」的定義一起錯，對照永遠一致。另外，200 組隨機實例很少出現「中段長等待＋緊工時」的組合。
- **解法**：改用前向時間餘裕；參考窮舉器改用**不同演算法**（反向「最晚開始」）實作同一個語意；新增專門逼出中段等待的 `TwoShiftInstance` 情境（舊評估器 86/120，新 120/120）。commit `1a25bf2`。
- **教訓**：
  1. 參考實作要獨立的不只是「程式碼」，還有「語意假設」。政策性的選擇（像出發時刻）要明確寫成規格，再讓兩邊各自用不同方法實作。
  2. 隨機測試的分佈要涵蓋目標領域的典型情境。送餐有兩個餐次，「中段長等待」是常態，不是邊界情況。

### 坑 2：修了一個語意 bug，在時間相依路網上引入效能退步

- **症狀**：坑 1 的修正通過所有測試，但重跑大型範例時，60 秒最佳化的總行車從 17:00 變成 18:12。用舊版 build 重跑仍是 17:00，排除隨機差異。
- **原因**：第一版只要「延後出發能讓工時變短」就接受。在時間相依路網上，延後可能讓車進入尖峰，行車時間變長。但目標的字典序是**行車在工時之前**，等於為了較次要的目標犧牲較重要的目標。窮舉測試都是靜態行車（所有出發時刻的行車相同），所以抓不到。
- **解法**：所有試過的出發時刻都是候選，依「符合工時上限 → 行車少 → 工時短」選擇（`RouteEvaluator.Preferred()`）。新增測試用的 `PeakOracle`（過了指定的尖峰時刻就降速，定義在 `tests/MealRoute.Tests/Evaluation/RouteEvaluatorTests.cs`）與兩個測試：延後進入尖峰「只為縮短工時」時不採用，「工時上限需要」時採用。commit `d433320`。
- **教訓**：
  1. 局部決策（評估器內選出發時刻）的比較順序必須與全域目標一致。
  2. 只有靜態測試不夠；時間相依的效果要在真實規模的範例上量測。量測時要比「相同迭代數」而不只是「相同時間」，才能把「每次迭代變慢」與「搜尋品質變差」分開。

### 坑 3：CI 上雜湊不符，本機正常

- **症狀**：加入範例後 CI 一直失敗，本機測試全過。失敗的是端對端測試，原因是路網檔的 SHA-256 與專案檔記錄的不同。
- **原因**：`.gitattributes` 的 `* text=auto` 讓 Windows runner 以 CRLF 簽出 `city.geojson`，位元組改變，雜湊就變了；本機工作目錄保留了 LF。
- **解法**：`*.geojson -text`、`samples/** -text`、`benchmarks/** -text`，資料檔不做換行轉換。同時加上「失敗時把 TRX 轉成 `::error` 註記」的 CI 步驟，讓原因直接顯示在執行頁面。commit `3771ba5`。
- **教訓**：任何被雜湊或位元組比對的檔案，都要在 `.gitattributes` 明確設為 binary／`-text`。CI 失敗時「本機正常」通常代表環境差異，先懷疑簽出設定與換行。

### 坑 4：路徑黑名單被繞過，三次 commit 才改成白名單

- **症狀**：專案檔是可分享的資料。若它參照的路網是 UNC 路徑（`\\server\share\...`），開啟專案時 Windows 會連線該主機，可能送出使用者的憑證。
- **演進**：
  1. commit `6f974a0`：拒絕 UNC 與裝置路徑（`\\server`、`\\?\`、`//host`）。
  2. commit `ff256db`：發現混合分隔符號（`\/host`、`/\host`）與前置空白可以繞過前綴檢查；改為正規化後再檢查，並加上 `Uri.IsUnc`，且對「完整解析後實際會開啟的路徑」再檢查一次。
  3. commit `a5bd6b8`：改成**白名單**：只有完整解析後在本機磁碟代號（且不是對應的網路磁碟機）或專案資料夾內才允許。
- **解法所在**：`PlanningWorkspace.IsAllowedReferencedPath()`。
- **教訓**：安全檢查用黑名單幾乎一定會漏（Windows 路徑的寫法太多）。直接定義「允許什麼」，並且對**最終實際使用的值**檢查，而不是對輸入字串檢查。

### 坑 5：CSV 公式注入

- **症狀**：名單的姓名、地址、備註是使用者輸入，路線 CSV 會在 Excel 中開啟；以 `=`、`+`、`-`、`@` 開頭的文字會被當成公式執行。
- **解法**：`CsvText.Escape()` 對文字欄加前置單引號，匯入時 `Unescape()` 移除，往返無損；數字欄不處理。先用在路線 CSV（commit `49e3b89`），再擴及名單 CSV（commit `6f974a0`）。
- **教訓**：匯出功能也是攻擊面。跳脫要「可逆」，否則會破壞匯出再匯入的往返需求。

### 坑 6：「必送站選哪個放棄」的結構性盲點（保險性修正）

- **症狀**：外部審查回報實例 43：必送站無法全部服務時，即使 10 萬次迭代也卡在次佳解。
- **原因**（推論）：repair 依層級與成本插入，必送站放不完時總是插回同一個必送站，而「換掉哪個必送站」會影響下一層目標（較小的必送站可能騰出空間給選送站）。
- **解法**：`AlnsRun.UnservedSwapPass()`：移除一個相關的已服務必送站、插入未服務的必送站、依優先權填選送站，精確目標變好就套用。commit `c181814`。
- **未解決的部分**：我們的產生器**無法重現**實例 43（新的「必送短缺」窮舉對照修改前後都是 150/150）。這個修正是依審查描述做的保險，以一個手工實例的單元測試證明「只有這個移動能在 Polish 中找到最佳解」。📄 本次開發對話與 commit 訊息。
- **教訓**：無法重現時，要誠實記錄「修了什麼、驗證了什麼、沒驗證什麼」，而不是宣稱已修好。

## 潛在風險（🔍 推斷）

- **L1 每對地點最多 255 條路徑**：超過會丟例外。實務上每對約 1–3 條，但極端的速度表（各時段差異很大）可能讓候選路徑變多。
- **`ExactOracle` 記憶表整批清空**：長時間使用 App（反覆拖曳、重新排程）時，可能週期性變慢。
- **參考實作的獨立性沒有測試保護**：日後有人在 `tests/MealRoute.Tests/Reference/` 中呼叫 Core 的演算法，測試會「一起對」而失去意義（坑 1 的教訓）。
