# 01 需求分析

> 本章的需求來源：開發前提供的規格（原文未存入 repo），由開發者整理成 `docs/01-system-analysis.md` 並在 2026-11-09 經使用者逐項確認；之後 2026-11-11 有一份外部審查報告，促成第 3 節的修訂需求。凡是只能從程式碼反推的項目，都標成 🔍。

## 1. 背景與目標

社區關懷據點每天中午與傍晚，要為 150–250 位獨居長者送餐。原本以紙本地圖人工排線，造成四個痛點：

| 痛點 | 系統要提供的能力 |
|---|---|
| 超時、湯冷掉 | 硬性時間窗、尖峰會變慢的行車時間、最長工時 |
| 漏送 | 「必送站全數服務」是最高優先的目標；送不到的站要列出原因 |
| 臨時延誤、車輛故障 | 當天重新排程，只動「還沒出發去服務」的站 |
| 社工需要人工微調 | 拖曳時 50 ms 內回饋、鎖定站點或整條路線 |

> 📄 依據：`docs/01-system-analysis.md` §1「問題陳述」。

## 2. 使用者與角色

| 角色 | 做什麼 | 來源 |
|---|---|---|
| 社工（排班者） | 匯入路網與名單、最佳化、拖曳調整、重新排程、列印 | 📄 `docs/01-system-analysis.md` §1、§2 |
| 駕駛 | 只接收產出物（路線單），不操作系統 | 📄 同上 |
| 開發／驗收者 | 產生合成城市與名單、跑 Solomon 基準 | 📄 同上 §2 UC8、UC9 |

系統是**單機、單一使用者**，沒有登入、帳號或權限。📄 同上 §1。

## 3. 功能需求

| 編號 | 需求 | 來源 |
|---|---|---|
| FR-01 | 匯入 GeoJSON 路網（LineString，屬性 `id`、`oneway`、`class`），建立有向圖；無效幾何要逐筆回報 feature 索引與 id，不可崩潰 | 📄 `docs/01-system-analysis.md` UC1、§4.1 |
| FR-02 | 找出強連通分量（SCC），把與主路網不互通的小分量列為警告並在地圖標示 | 📄 同上 §4.2 |
| FR-03 | 站點與據點吸附到最大 SCC 上最近的路段；距離超過 150 m 要警告 | 📄 同上 UC2、§4.3 |
| FR-04 | 行車時間依道路等級與 15 分鐘時段變化（96 個時段），且「晚出發不會早到」（FIFO） | 📄 同上 §4.4 |
| FR-05 | 多車路線最佳化：兩種容量（餐盒、保溫箱）、車輛可用時段、最長工時、硬性時間窗、必送／選送（優先權 1–5）、駕駛休息規則 | 📄 README「功能」、`docs/01-system-analysis.md` §4.7–4.9 |
| FR-06 | 目標依字典序：未服務必送站數 → 未服務選送優先權總和 → 使用車輛數 → 總行車時間 → 總工時 | 📄 同上 §4.8 |
| FR-07 | 最佳化可設定時間上限與種子、背景執行、進度單調遞增、隨時取消；取消時保留目前最佳的**完整可行解** | 📄 同上 UC3、§4.9 |
| FR-08 | 拖曳站點時即時顯示可行性、五項指標變化與「第一個違反的條件」（例如「王奶奶 12:10 到，時間窗 11:30–12:00」） | 📄 同上 UC4、§4.11 |
| FR-09 | 鎖定站點（原車、原位置）與鎖定整條路線；重新最佳化時保持不變 | 📄 同上 §4.10 |
| FR-10 | 當天重新排程：輸入車輛、回報時刻、位置、已完成站、延誤分鐘或故障，只重排尚未出發服務的站 | 📄 同上 UC5、§4.12 |
| FR-11 | 每位駕駛一份可列印的路線單；路線 CSV（UTF-8 with BOM）與 GeoJSON 匯出，且可再匯入 | 📄 同上 UC6、§4.13 |
| FR-12 | 專案檔（JSON）存讀：路網參照、名單、車輛、解、鎖定；版本過新或損毀要給明確訊息 | 📄 同上 UC7、§4.14 |
| FR-13 | 地圖與時間軸（甘特圖）點選聯動 | 📄 README「功能」、`docs/02-architecture.md` §4 |
| FR-14 | 合成城市與名單產生器、Solomon VRPTW 基準（靜態模式）與最佳已知解比較 | 📄 `docs/01-system-analysis.md` UC8、UC9 |
| FR-15 | 復原／重做手動調整 | 📄 README「功能」；🔍 規格中是否明列不確定，`docs/01-system-analysis.md` 沒有對應的 UC 或驗收項目 |
| FR-16 | CLI 輸出的吸附警告要顯示站名，而不是內部索引（L0、L1…） | 📄 外部審查報告的次要項目，使用者於 2026-11-11 要求修正（commit `ce59bfe`） |

### 3.1 2026-11-11 審查後補充的需求

外部審查指出兩個語意問題，使用者要求修正：

| 編號 | 需求 | 來源 |
|---|---|---|
| FR-05a | 出發時刻是**決策變數**：路線中段的長等待（例如午餐與晚餐時段之間）也要能以延後出發吸收，不能讓可行路線被判成超過工時 | 📄 本次開發對話中使用者轉述的審查報告；commit `1a25bf2` |
| FR-05b | 必送站無法全部服務時，要能選擇「放棄哪一個」必送站，使下一層目標更好 | 📄 同上；commit `c181814` |
| FR-17 | 提供測試報告與 CI 執行連結 | 📄 同上；commit `1ce58a0`、`2794adc` |

## 6. 未解決或待確認的需求問題

- **休息只能在站點服務後**：位置回報點不是站點時，車輛不能在該處休息；回報時累計行車已接近 4.5 小時，第一段路就可能被判不可行。📄 README「已知限制」。這是規格語意下的限制，是否需要「路邊休息」尚未討論。
- **時間上限下的結果不可重現**：要完全重現必須用迭代上限。📄 README「已知限制」。實務上社工會用時間上限，是否需要提示「本次結果無法重現」未討論。
- **審查報告的實例 34、43 沒有原始資料**：只能用同類情境的窮舉測試重現。📄 本次開發對話。
- 🔍 **兩個餐次（中午、傍晚）如何對應到資料**：程式中一份專案就是一組名單與車輛，沒有「餐次」欄位；推測社工是每個餐次各建一個專案，或像 `TwoShiftInstance` 測試那樣把兩段時間窗放在同一天的名單中。需求來源沒有說明。
